## Full-Pass-8 technique rotation

This revisit intentionally differs from Full Pass 7's temporal-cut, queue-network and causal/counterfactual emphasis. It combines elicitation completeness subtraction, release-set/attestation-set algebra, trust-horizon mutation, Brownfield archive reconstruction, channel/cohort divergence, evidence-provider differential, offline verification partition, operational-readiness fracture and AI/low-code promotion composition.

1. **release-set / evidence-set subtraction** — define the intended release as a set of subjects/variants/platforms, then subtract one artifact, SBOM, provenance statement, signature/referrer or verifier profile while leaving the visible release label unchanged;
2. **attestation identity permutation** — vary subject digest, predicate type, statement issuer, builder identity, signer identity, certificate identity/issuer, verifier policy and promotion actor independently to reject identity transitivity;
3. **trust-horizon mutation** — hold historical signing/timestamp evidence constant while changing current trust roots, certificate/identity status, revocation/withdrawal policy, release authority or verifier policy revision;
4. **mutable-reference alias attack** — preserve a human release name/channel/tag while mutating target digest, provider namespace or cohort assignment; compare immutable subject identity with mutable distribution references;
5. **channel/cohort divergence** — canary/staged/general/offline cohorts receive different artifacts/evidence or remain residual while a central promotion projection says complete;
6. **provider evidence differential** — copy identical artifact bytes across registries/providers while referrer discovery, retention, alias history, transparency/timestamp access or policy-verifier integration differs;
7. **Brownfield release reconstruction** — inventory old registries, file shares, hand-carried artifacts, manual checksums, email/ticket approvals, handwritten runbooks and vendor release archives while preserving `observed historical procedure != approved canonical release semantics`;
8. **operability elicitation subtraction** — remove release owner/on-call, rollback eligibility, withdrawal/revocation response, evidence retention, queue SLO, provider quota, offline verification path, residual-cohort reconciliation or post-change validation from an otherwise feature-complete release design;
9. **queue/capacity asymmetry** — vary signing/HSM, SBOM generation, scanning, transparency/timestamp, registry publication and promotion queues independently; test hidden tail/backlog, priority inversion, retries and provider quota saturation behind healthy aggregate utilization;
10. **offline/autonomous verification partition** — local runtime retains pinned artifact/evidence while Fleet/registry/trust network is unavailable; distinguish local execution continuity from current global release eligibility;
11. **Physical/Peripheral integration boundary** — adapter artifacts for VMS/BMS/access/PDV/biometric connectors may be signed and observed, but artifact trust never implies central device actuation authority;
12. **AI/low-code promotion composition** — AI can infer candidate signer/provider/channel/promotion choices but cannot strengthen partial evidence, current authority, trust or semantic compatibility;
13. **proof-domain attack** — attempt to promote successful artifact verification, SBOM completeness or release admission into deployment convergence, runtime adoption or `WorkflowCompletionCertificate` truth and require rejection.

## Operability Elicitation Lens — capability-specific questions

Production readiness is separate from feature completeness. For Artifact/Release/SBOM/Provenance, elicitation should explicitly ask:

- **OBSERVABILITY:** How do we know artifact publication, evidence attachment/discovery, promotion and cohort pickup are functioning? Which statuses expose source, subject, provider and freshness?
- **OWNERSHIP:** Who owns build output, SBOM/provenance, signer identity, release approval, provider account, withdrawal, rollback and incident escalation? Who is on call for failed urgent release?
- **FAILURE_HANDLING:** What happens on partial upload, ambiguous provider acknowledgement, signature/timestamp failure, incomplete referrer discovery, scan timeout or provider outage? What remains `UNKNOWN`?
- **RECOVERY:** How are interrupted publications reconciled? What makes rollback/withdrawal eligible? How are lost evidence links or corrupted metadata rebuilt without inventing historical truth?
- **CAPACITY:** Expected and peak release rates? Artifact sizes? Scan/signing/HSM/provider quotas? Queue SLO, burst tolerance, headroom and security-fix priority?
- **CURRENTNESS:** What is the acceptable age for trust material, vulnerability/admission evidence, provider inventory, channel resolution and cohort status? How are stale dashboards shown?
- **SECURITY:** Which signer/trust roots/issuers are allowed? How are revocation, rotation, compromised signer/provider and suspicious promotion handled?
- **RECONCILIATION:** How are release manifest, subjects, attestations, registry/provider inventory and deployed residual cohorts compared? Who owns unresolved drift?
- **CHANGE_SAFETY:** Canary/staged promotion? Mixed-version compatibility? rollback/withdrawal proof? post-change validation? maintenance windows?
- **COST:** Which provider/storage/scan/signing/egress dimensions are observed? How are quota/cost anomalies surfaced without turning observability into pricing authority?
- **DOCUMENTATION:** Which runbooks/evidence profiles are revisioned? How are Brownfield/manual release procedures represented and contradictions surfaced?
