# Station S3 R5 — Template / Full View Kickoff 01

Status: research evidence; non-authoritative until S3 synthesis/materialization.
Base: `main@19c87172c19e9bae5bf39848a0db9d09798705ce`.

## Station current -> R5 question

R1-R4 establish a bounded ladder through C6 Pattern, with identity != placement != presentation != action, Station without Core/business authority, and projection state unable to establish canonical truth. R5 asks when a reusable composition of regions/patterns deserves promotion to C7 Template/View rather than remaining a configured composition.

Initial repository census found no already-promoted Station product Template/View contract on fresh main. Generic project/schedule templates are documentation infrastructure and are not Component Grammar evidence. Existing task specs also explicitly kept Template Manager and Window/View Editor out of earlier construction scope. Therefore R5 must not infer product authority from the word `template`.

## Candidate C7 distinction

A C7 Template/View is a reusable full-view composition contract only when it adds all of:

1. stable semantic identity independent of window geometry and current placement;
2. declared region/pattern roles and compatibility constraints;
3. reusable variation points that do not require cloning a domain-specific component tree;
4. responsive/discrete execution semantics derived from the composition grammar rather than arbitrary pixel geometry;
5. deterministic manual authoring/editing semantics;
6. a proof delta beyond the inherited C0-C6 obligations.

Changing labels, domain nouns, icon/color, current target, pane side/width, span values within an admitted range, or command binding alone is configuration and does not create a new Template/View.

## Projection and source hypothesis

R5 will test a single-authority model:

`canonical artifact identity + revision -> Inspector | Layers | Graph | visual preview | source/YAML projections`

Edits from any admitted projection must return through one owning mutation/command boundary and produce one new canonical revision before projections refresh/regenerate. A projection revision never becomes canonical artifact authority. Source/YAML is therefore initially classified as a projection/authoring surface candidate, not an independent source of truth; R5 must test whether round-trip requirements force a different contract.

## Proof Grammar — inherited proofs

C7 may inherit lower-level proof only when preconditions remain unchanged:

- C0-C2 token/primitive/compound semantics and accessibility;
- C3 grouping/collection compatibility;
- C4 command identity, target/currentness, availability != authority, owner revalidation, result non-strengthening;
- C5 named-region anatomy and bounded presentation ownership;
- C6 contextual-pattern participant roles and action-family dedup;
- projection/source identity, revision/currentness separation where an existing owner already proves those invariants.

No inherited proof authorizes semantic reparent/order, Core/business authority, persistence/publish semantics, or a second state authority.

## C7 smallest delta-proof candidates

Coverage starts `unproven-gap` unless repository evidence proves otherwise.

| Concern | Initial coverage | Smallest future proof |
|---|---|---|
| template identity survives admitted placement/layout variation | unproven-gap | vary placement/span within contract and preserve template/view identity |
| declared roles reject incompatible composition | unproven-gap | invalid region/pattern participant fails deterministically without silent fallback |
| variation != new component/template | unproven-gap | two domain configurations share the same C7 identity/contract without feature-name branching |
| responsive execution preserves semantic roles | unproven-gap | discrete/span transition changes presentation without changing semantic identity/action binding |
| Inspector/Layers/Graph/preview/source address same canonical nodes | unproven-gap | selection/edit round-trip resolves the same canonical node refs across projections |
| projection edit is single-authority | unproven-gap | one admitted projection edit yields one canonical mutation/revision, then projection refresh |
| stale source/projection cannot overwrite current artifact | unproven-gap | stale revision edit is rejected/reconciled by owner; presentation cannot self-promote currentness |
| manual undo/history semantics | unproven-gap | accepted edit has deterministic history/undo behavior at the owning boundary, without presentation-only rollback claims |
| human acceptance | not-applicable to machine conformance | separate acceptance journey validates that the resulting view matches intended UX |

Absence of evidence is never PASS.

## Dedup / promotion guard

Reject by default domain-specific names such as `ApprovalTemplate`, `TicketView`, `CrudTemplate`, `DashboardTemplate`, or `DeploymentView` when the same C7 contract plus configuration/bindings expresses the case. Promote only when a candidate introduces a reusable semantic invariant and independent proof delta that cannot be expressed by existing roles, variants, bindings or configuration.

## Grammar Sufficiency Test — R5 pressure

R5 will attempt the same five materially distinct classes without escape hatches:

- document approval;
- ticketing;
- CRUD/editor;
- operational dashboard;
- deployment configuration.

Measure coverage and gaps. Do not use a synthetic score. A new abstraction is justified only by a repeated semantic/proof gap across these exemplars, not because a benchmark exposes a feature.

## Benchmark extraction plan

Use mature editors/builders (Figma, Webflow, Framer and comparable low-code editors) to answer: what is stable view/template identity; how roles/slots and variants are constrained; how responsive authoring is represented; how visual/source projections synchronize; what manual insertion/selection/tree/Inspector/preview/history flows exist. Use VS Code/JetBrains/Adobe/Blender/CAD-class workstations to challenge full-view/workspace assumptions, especially tabs/editors/panes/workspaces and restoration/currentness. Classify each finding own/adapt/adopt-pattern/defer and record convergence, divergence, proof obligations, inherited proofs and gaps. Do not copy provider catalogs or provider-specific schemas.
