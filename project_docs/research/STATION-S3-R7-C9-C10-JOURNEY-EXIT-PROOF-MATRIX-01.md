## Purpose

Turn C9 Application and C10 Studio hypotheses into representative journeys, inherited proofs, delta obligations, explicit gaps, dedup pressure and R7 exit criteria. Incorporates the bounded client-deliverable Tool pressure case requested during R7 review. No Studio is constructed and no Core/business authority is created.

## Coverage discipline

Coverage uses proven, failed, unproven-gap, or not-applicable. Missing evidence is never PASS. Human acceptance remains distinct from machine conformance. Lower-level proofs are reused only when preconditions are unchanged.

## C9 journeys

- Application identity under label/icon/layout changes: proven only for the bounded current runtime identity tests.
- Declared Tool contribution compatibility: unproven-gap; semantic incompatibility must fail before activation.
- Artifact/context entry routing: unproven-gap; routing must be deterministic without Station owning canonical state.
- Single/multi-instance launch: proven only for bounded launch-policy behavior independent of identity.
- Restore/reopen: unproven-gap; presentation/configuration may restore, canonical context must be revalidated.
- Contribution command invocation: unproven-gap; contributions must not bypass command/capability registries or the authority owner.
- Save/readback/version: unproven-gap; stale revision must be explicit and silent last-write-wins is not assumed.
- AppManifest versus ComponentRegistry: unproven-gap end-to-end; manifest resolution must not create component species.

## C10 journeys

C10 remains a promotion hypothesis, not an automatic requirement. Shared work context, Tool-local versus shared context isolation, cross-Tool consequence propagation, stale/partial/unknown result preservation, presentation-only rearrangement, restoration currentness and bounded cross-Tool navigation are all unproven-gap.

The smallest C10 proof is that multiple Tools resolve one canonical work reference/revision and one authoritative result drives affected projections without duplicated truth or local strengthening.

## Client-deliverable Tool pressure

R7 must test an operational Work Order Workspace composed from reusable C8 Tool families such as Asset Explorer, Document Viewer, Annotation, Checklist, Measurement, Diagnostic and Timeline. This challenges the assumption that produced systems are only transactional pages/forms.

Builder Tool, Runtime/Client Tool and Shared Tool are research classifications, not new grammar levels. Default hypothesis: destination is metadata or packaging policy on C8 Tool. Synthesis may promote a distinction only if materially different lifecycle/ownership/proof invariants recur and configuration cannot express them.

Runtime delivery remains unproven-gap for capability binding, state ownership, persistence/readback/currentness, keyboard/accessibility, recoverability, canonical artifact integration, provider-independent packaging and proof inheritance. Produced runtime must remain independent of Station construction/editor and research/QA internals.

## Dedup and sufficiency

Reject domain-named Application/Studio species and destination-specific duplicate Tool species when configuration, binding or packaging expresses the difference. C8→C9 requires a reusable application lifecycle/assembly invariant plus delta proof. C9→C10 requires a reusable shared-work-context/cross-Tool invariant plus delta proof.

Grammar Sufficiency remains candidate sufficiency / unproven-gap for document approval, ticketing, CRUD, operational dashboard and deployment configuration. Add the Work Order Workspace as a bounded operational/client-tooling pressure case; failure identifies a concrete grammar gap, not automatic authority to create a new abstraction.

## R7 exit

R7 handoff requires fresh-main/document reconciliation, C9 runtime census, Core reuse/projection census, this journey/proof matrix, adversarial sufficiency mapping including the operational client-tool case, explicit carry-forward of unresolved gaps and exact-head CI evidence. No Studio Construction or new Core/business authority.

Integrated R7 unlocks R7B, not synthesis directly. R7B must benchmark engineering/product-factory workbenches and client-tool destination/lifecycle pressure. Synthesis must materialize the Decision Graph and decide whether Tool destination is metadata/configuration or a genuine grammar distinction. Construction remains blocked until the full S3 planning exit gate, intermediate Test Review/Hardening planning and final QA Coverage/Evidence Review planning are satisfied.
