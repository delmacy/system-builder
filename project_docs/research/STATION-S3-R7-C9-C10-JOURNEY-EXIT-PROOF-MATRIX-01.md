## Coverage discipline

Coverage uses proven, failed, unproven-gap, or not-applicable. Missing evidence is never PASS. Human acceptance remains distinct from machine conformance. Lower-level proofs are reused only when preconditions are unchanged.

## C9 journeys

- Application identity under label/icon/layout changes: proven only for the bounded current runtime identity tests.
- Declared Tool contribution compatibility: unproven-gap; semantic incompatibility must fail before activation.
- Artifact/context entry routing: unproven-gap; routing must be deterministic without Station owning canonical state.
- Single/multi-instance launch: proven only for bounded launch-policy behavior independent of identity.
- Restore/reopen: unproven-gap; presentation/configuration may restore, canonical context must be revalidated.

## C10 journeys

C10 remains a promotion hypothesis, not an automatic requirement. Shared work context, Tool-local versus shared context isolation, cross-Tool consequence propagation, stale/partial/unknown result preservation, presentation-only rearrangement, restoration currentness and bounded cross-Tool navigation are all unproven-gap.

The smallest C10 proof is that multiple Tools resolve one canonical work reference/revision and one authoritative result drives affected projections without duplicated truth or local strengthening.

## C9 Application versus C10 Studio authoring-regime hypothesis

R7 records a sharper adversarial hypothesis for R7B: the promotion boundary may be a change in **work regime over the artifact**, not Tool count, visual richness, or domain naming.

- C9 Application may primarily consume, present, execute or perform bounded interventions on an artifact/context (reader/player/runner behavior can still include annotations, metadata edits, print/export or other bounded commands).
- Candidate C10 Studio may represent a coordinated authoring work context in which multiple reusable Tools structurally transform one versioned working artifact/definition and materialize a new revision.
- Tool count is explicitly non-discriminating: a feature-rich reader remains C9 if the authoring invariant is absent; a smaller workbench may qualify for C10 only if the invariant is proved.
- Editing alone is non-discriminating. A single annotation, rename or metadata update does not promote C10.
- Candidate C10 delta to falsify in R7B: shared working artifact/context + structural mutation + coordinated multi-Tool editing + authoring history/version lifecycle + materialization/publication of a new revision.
- Useful heuristic, not a contract: an Application often operates the object; a Studio may operate the object's editable definition/structure. CAD/media cases must challenge this wording because direct artifact editing may still be Studio-like.
- Reader/Player/Runner/Worker/Editor/Versioner remain roles or capability envelopes unless materially distinct identity/lifecycle/ownership/proof invariants force promotion. Do not create new grammar levels from these names.

Candidate acceptance journeys:

- open artifact@R17 -> reader projection resolves R17 -> navigation/annotation/print changes only declared bounded state and never silently creates authoring authority.
- open artifact@R17 for authoring -> one working context is established -> all participating Tools resolve the same working identity/revision.
- Tool A structurally edits the working artifact -> one admitted authoring mutation/revision occurs -> Tool B/Layers/Inspector/Preview invalidate or regenerate from that same revision.
- undo/redo request -> authoring history owner applies or rejects it -> projections converge without treating business compensation as editor undo.
- publish/save materialization -> owning contract validates currentness -> artifact@R18 is produced or rejection remains explicit; no visual success substitutes for authoritative result.
- rearrange/hide/restore Studio Tools -> presentation changes -> working artifact identity, revision and authority remain unchanged; restored projections revalidate currentness.

This is research evidence only. R7B must actively seek counterexamples in PDF/document editors, IDEs, CAD/CAE, media editors, Unreal-like workbenches, MPS/Sirius and low-code/modeling environments. If C9 + Tool/configuration already expresses the full regime without a reusable semantic delta, C10 must not be promoted.

Produced runtime must remain independent of Station construction/editor and research/QA internals.

## Dedup and sufficiency

Reject domain-named Application/Studio species and destination-specific duplicate Tool species when configuration, binding or packaging expresses the difference. C8→C9 requires a reusable application lifecycle/assembly invariant plus delta proof. C9→C10 requires a reusable shared-work-context/cross-Tool invariant plus delta proof.

Grammar Sufficiency remains candidate sufficiency / unproven-gap for document approval, ticketing, CRUD, operational dashboard and deployment configuration. Add the Work Order Workspace as a bounded operational/client-tooling pressure case; failure identifies a concrete grammar gap, not automatic authority to create a new abstraction.

## Adversarial coherence and testability carry-forward

This matrix carries the full C0-C10 grammar under one rule: a higher level may inherit a lower proof only while the lower invariant and its preconditions remain unchanged. A visually plausible composition is never semantic evidence by itself.

| Level | Smallest proof obligation | Primary adversarial failure |
|---|---|---|
| C0 | stable semantic identity independent of label/placement | IDs coupled to location or presentation |
| C1 | bounded primitive variant/state with preserved accessibility semantics | semantic intent disguised as a variant; primitive explosion |
| C2 | typed slot/span compatibility and fail-closed invalid composition | incompatible slot, invalid variant, arbitrary geometry |
| C3 | explicit collection/topology/order ownership | layer/order drift or visual order silently becoming semantic order |
| C4 | one command/target/currentness/authority/effect/result chain | duplicated interaction capability; accepted strengthened to effective |
| C5 | Region identity independent of placement plus bounded focus/visibility/restoration | pane side/size promoted to semantic identity; stale restore |
| C6 | reusable participant relationship with substitutable roles | domain-named pattern explosion or duplicated action species |
| C7 | definition/instance identity, typed roles and one-authority multi-projection currentness | YAML/Layers/Inspector/Preview becoming parallel truths; responsive semantic deformation |
| C8 | Tool identity, active-context routing and cross-surface command convergence | toolbar/menu/keyboard divergence; focus mistaken for authority |
| C9 | Application lifecycle/assembly, compatible contributions and deterministic entry without registry mutation | AppManifest conflated with ComponentRegistry; contribution bypass |
| C10 | reusable shared authoring/work-context delta beyond C9 configuration | Studio promoted from Tool count, layout richness or branding rather than semantics |

### Cross-level invariants

- one canonical authority, many projections;
- a projection cannot establish canonical truth or strengthen stale/partial/unknown/rejected evidence;
- one accepted projection mutation produces at most one owning canonical mutation/revision, followed by deterministic invalidation/regeneration of admitted projections;
- semantic IDs do not encode window, pane, layer, row, column or responsive placement;
- responsive relocation changes representation/placement, not identity, command target or authority;
- semantic reparent/order remains blocked until cycle, reachability and sibling-order contracts are proved;
- authoring undo/redo is not business compensation; retry/compensation remains owner-controlled and currentness-revalidated;
- `ComponentRegistry != AppManifest` and `WindowGeometry != composition grid` remain non-negotiable.

### Test matrix

| Test class | Required evidence |
|---|---|
| contract/unit | identity stability; bounded variants; currentness; duplicate/reference rejection; authority-shaped field rejection; command/qualifier invariance |
| schema/composition invariants | typed-slot compatibility; invalid variant fail-closed; topology/order invariants; no ID/location coupling; manifest/Tool compatibility |
| component interaction | multiple surfaces/projections resolve the same canonical references and command/target/owner; focus/context scopes applicability only |
| Playwright journeys | action -> expected state change for entry, edit, Tool switch, restore/revalidate, stale rejection and projection convergence |
| visual/structural regression | detect span/order/responsive deformation only; never use pixels as proof of canonical truth/effectiveness |
| accessibility | region naming, landmarks, reading/focus order, keyboard equivalence, focus entry/exit/restoration and responsive preservation |
| Station/Core integration | Station cannot strengthen authority/result semantics; accepted != effective; stale/partial/unknown preserved; retries/compensation owner-controlled |

### Human-readable acceptance journeys

- move a component between admitted placements -> placement changes -> semantic ID and command target remain unchanged;
- request an invalid variant -> validation rejects -> zero canonical mutation;
- insert an incompatible participant into a typed slot -> composition rejects before mutation -> existing canonical artifact remains unchanged;
- visually reorder Layers without an admitted semantic-order capability -> presentation may change -> canonical sibling order remains unchanged;
- change desktop to compact arrangement -> spans/placement adapt -> semantic IDs, roles, commands, focus reachability and reading semantics remain preserved;
- edit one admitted projection -> one owning mutation/revision occurs -> YAML/Layers/Inspector/Preview invalidate or regenerate from that revision;
- submit a stale YAML/Inspector/projection edit -> currentness check rejects/reconciles -> zero silent overwrite;
- invoke one action by keyboard, menu, toolbar or contextual surface -> same command identity/target/owner resolves -> same authoritative result semantics are projected;
- receive PARTIAL/UNKNOWN/stale from the owner -> all projections preserve that state -> no success styling or message may strengthen it;
- restore a workspace -> presentation/configuration returns -> canonical artifact/context is revalidated before authoritative interaction;
- open an Application manifest with an unknown/incompatible Tool -> activation rejects -> ComponentRegistry and canonical business state remain unchanged;
- structurally edit a candidate Studio working artifact -> one authoring revision occurs -> all participating Tools converge on the same working revision;
- publish a candidate Studio artifact -> owner validates currentness -> a new canonical revision is materialized or rejection remains explicit.
