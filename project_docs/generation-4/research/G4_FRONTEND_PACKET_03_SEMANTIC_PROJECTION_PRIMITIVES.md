## 1. Objective

Materialize the smallest lower/middle-level semantic projection contracts required before the Main Composition Canvas 3D can legitimately be promoted into Module Components, Tools or Workspaces.

This packet deliberately does **not** plan a complete Canvas. It qualifies the primitives that preserve semantic identity, selection, typed connection eligibility, floor manifestation and critical gate meaning across 2D/3D/textual projections and across semantic zoom/aggregation boundaries.

Core question:

`How can one canonical semantic object be represented, selected, related and simplified across projections without renderer identity, visual adjacency, LOD or camera state becoming semantic truth?`

## 4. Scope

### 4.1 ProjectionIdentityRef — PRIMITIVE

Purpose: stable projection-facing reference that maps a rendered/list/table/graph representation back to canonical semantic identity plus qualified projection context.

Candidate information to research, not schema-authorize:

```text
semanticIdentity
projectionKind
projectionContext
revision/currentness qualification
representationIdentity?
disclosure qualification
source/evidence ref?
```

Must prove renderer object IDs, mesh IDs, DOM IDs and aggregate IDs cannot silently become canonical identity.

### 4.2 SelectionBridge — COMPONENT

Purpose: preserve focus/selection/primary-selection identity when representation changes across 2D/3D/textual views, semantic zoom, clustering, floor isolation or camera transitions.

Must distinguish:

```text
hovered
focused
selected
primary selected
attention/highlighted
hidden-by-disclosure
not-representable-in-current-view
```

`focus != selected != hovered != attention`.

### 4.3 QualifiedRelationPort — COMPONENT

Purpose: semantic contract behind horizontal `+` relation/composition affordances.

Required candidate transition family:

```text
IDLE
-> CANDIDATE
-> QUALIFYING
-> ELIGIBLE | INELIGIBLE(reason) | UNKNOWN(needs qualification)
-> PROPOSED
-> SUBMITTED
-> ACCEPTED | REJECTED | UNKNOWN_OUTCOME
-> EFFECTIVE | PARTIAL | FAILED | RECONCILING
```

The visual port does not grant compatibility or authority.

### 4.4 FloorManifestationPort — COMPONENT

Purpose: semantic contract behind vertical `+`, proposing a permitted manifestation/projection of an identity on another typed floor.

Must distinguish at least:

```text
TARGET_FLOOR_CANDIDATE
QUALIFYING
ELIGIBLE_SAME_IDENTITY
ELIGIBLE_DERIVED_IDENTITY
INELIGIBLE
UNKNOWN
PROPOSED
SUBMITTED
ACCEPTED
REJECTED
EFFECTIVE
PARTIAL
FAILED
RECONCILING
```

`Vertical manifestation != duplication`.
`Vertical alignment != ownership`.

### 4.5 CriticalStateMarker — COMPONENT

Purpose: preserve critical semantic/operational meaning when detailed geometry is simplified, clustered, hidden by semantic zoom, or represented textually.

Minimum candidate conditions:

```text
BLOCKED
UNKNOWN_OUTCOME
STALE
DRIFTED
CONFLICTED
MISSING_EVIDENCE
RECONCILIATION_REQUIRED
AUTHORITY_LIMITED
```

The marker is representation, not the state owner.

## 6. Research questions

1. What is the minimum identity tuple necessary to hand selection across projections without copying domain truth into the UI model?
2. How does selection survive `mesh -> cluster -> marker -> list row` substitution?
3. How is `not currently representable` distinguished from `deleted`, `hidden`, `no-access`, `filtered`, and `stale`?
4. Which relation-port states belong to interaction, semantic qualification, authority/availability, async acknowledgement and effect?
5. What proof makes a horizontal candidate `ELIGIBLE` rather than merely visually connectable?
6. What proof makes a vertical manifestation valid on a target floor, and when does it preserve identity vs create a derived identity?
7. How are UNKNOWN, PARTIAL and stale qualification carried through relation/manfiestation proposals without being strengthened?
8. Which critical states require a representation floor under semantic zoom/aggregation?
9. How does a critical marker remain keyboard/text accessible without duplicating state ownership?
10. How do revision/currentness changes invalidate or requalify an existing projection/selection/port candidate?

## 9. Transition proof obligations

Construction A must explicitly document valid, invalid and recovery transitions for each element.

Mandatory adversarial transition cases:

1. focus moves without selection change;
2. selection survives representation substitution;
3. selected identity becomes not representable in destination projection;
4. stale/currentness change invalidates a previously eligible port candidate;
5. relation candidate is visually adjacent but INELIGIBLE;
6. qualification result is UNKNOWN and submission is attempted;
7. SUBMITTED receives ACK but effect remains UNKNOWN/PARTIAL;
8. target floor becomes ineligible after proposal but before effect;
9. aggregate replaces member meshes while one member remains selected;
10. critical BLOCKED/UNKNOWN marker crosses LOD boundary and must remain discoverable;
11. permission/authority changes while a candidate is pending;
12. recovery/reconciliation cannot silently convert historical UNKNOWN into EFFECTIVE without evidence.

## 10. Failure / recovery

Research at minimum:

- renderer/picking failure with semantic model still available;
- projection mapping missing/ambiguous;
- selected object unavailable in destination projection;
- qualification service unavailable;
- stale revision discovered mid-interaction;
- duplicate activation while pending;
- relation/manfiestation outcome unknown after ACK;
- clustering/LOD change during interaction;
- recovery after camera/representation transition interruption;
- offline/degraded projection with bounded cached evidence.

The UI must preserve work/selection where safe and expose uncertainty rather than fabricate success.

## 11. Accessibility obligations

- 3D must not be the sole semantic accessibility tree.
- Every named interactive component requires a keyboard/non-drag route.
- Selection/focus must be independently perceivable.
- Ineligible/unknown reasons must be text-discoverable where actionable.
- Critical state cannot rely on hue alone.
- Reduced motion must not alter semantic transitions.
- A textual/list/table/graph projection must be able to resolve the same `ProjectionIdentityRef` and receive selection handoff.
- Tiny scene ports cannot be the sole target for relation/manifestation actions.

## 12. Performance obligations

This packet does not benchmark a renderer, but A/B must ensure component semantics survive the planned workload envelope.

NORMAL research envelope:

```text
50-200 modules
5-10 floors
hundreds of relations/ports/handoffs
thousands of simple visible primitives
```

STRESS research envelope:

```text
~1000 modules
thousands of relations
aggregation/clustering required
```

Required findings:

- stable semantic identity cannot depend on mesh/component instance lifetime;
- selection must survive instancing and LOD substitution;
- critical marker representation floors survive clustering;
- label/geometry suppression cannot become semantic omission;
- picking/selection mapping must remain bounded enough to avoid one React state subscription per primitive as a semantic requirement;
- render-on-demand must not suppress state/currentness updates.

`Large-scene degradation -> aggregation, not silent omission`.
